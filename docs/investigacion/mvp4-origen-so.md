## A. Instalar desde ISO
**Listar ISOs.** [H] `GET /nodes/{n}/storage/{s}/content?content=iso` («List storage content»); permiso `Datastore.Audit` **o** `Datastore.AllocateSpace` en `/storage/{s}`; cada volumen pasa además por `check_volume_access`, que para `iso`/`vztmpl`/`import` exige lo mismo («require at least read access to storage, (custom) templates/ISOs could be sensitive») [SC][SS]. Campos devueltos: `volid`, `format`, `size`, `ctime`, `notes`, `protected`… (no hay campo `content`) [SC]. [H] Un ISO es `storage:iso/<nombre>` con extensión `.iso` o `.img` (`ISO_EXT_RE_0 = qr/\.(?:iso|img)/i`) [SS]; en disco vive en `template/iso/` (`$vtype_subdirs`) [SP Plugin.pm].

**Montar como CD.** [H] Disco con `media=cdrom`: `ide2=local:iso/x.iso,media=cdrom`. Si se pasa un ISO sin `media=cdrom` la API falla: «explicit 'media=cdrom' is required for iso images» [QA `check_drive_param`]. `media` admite `cdrom|disk`, por defecto `disk` [QD]. `cdrom` es alias de `-ide2` [DQ]. Un volumen existente usado como disco debe ser de tipo `images` o `iso` («content type needs to be 'images' or 'iso'») [QA `check_storage_access`]. `ide2=none,media=cdrom` no requiere nada; el CD físico (`cdrom`) exige `Sys.Console` en `/` [QA].
**Permisos al crear con ISO.** [H] En `POST /nodes/{n}/qemu` el acceso al ISO lo decide `check_volume_access` → `Datastore.AllocateSpace` o `Datastore.Audit` en `/storage/{s}` del ISO [QA][SS]. [H] `check_vm_modify_config_perm` **omite** los nombres de disco (`next if is_valid_drivename($opt)`, «some checks (e.g., disk, serial port, usb) need to be done somewhere else, as there the permission can be value dependent») y también `cdrom` [QA]: al crear **no** hace falta `VM.Config.CDROM` (coherente con F1: tampoco `VM.Config.Disk` para discos). [H] Al **modificar** una MV existente (`PUT …/config`) sí: `$check_drive_perms` exige `VM.Config.CDROM` si es CD y `VM.Config.Disk` si es disco [QA]. [LAB] confirmar la ausencia de `VM.Config.CDROM` al crear.
**Orden de arranque.** [H] `boot=order=scsi0;ide2;net0` («The guest will attempt to boot from devices in the order they appear here»; `legacy=` obsoleto) [QS][DQ]. **Nuevo privilegio:** `boot` está en `$diskoptions = { boot, bootdisk, vmstatestorage }` → exige **`VM.Config.Disk`** [QA]. El rol mínimo de 10 privilegios del MVP 1 no lo tiene: hay que añadirlo si la app envía `boot`. [LAB] confirmar. [I] Para instalar desde ISO basta `order=ide2;scsi0` (o `scsi0;ide2`: con disco vacío el firmware salta al CD; en OVMF el disco vacío no tiene entrada de arranque). Recomendación: `order=scsi0;ide2;net0` dejando el CD montado; tras la instalación el usuario arranca del disco sin tocar nada. [LAB] comprobar el comportamiento con OVMF y disco vacío.
**Segundo CD (virtio-win).** [H] Las guías oficiales W10/W11/W22/W25 añaden el CD de drivers «with Bus "IDE" and number 0» [W10][W11][W22][W25]; 9.2 hace IDE el valor por defecto para ese segundo CD [RM]. Límites por bus: IDE 4 (ide0–3), SATA 6, SCSI 31, VirtIO 16 [QD]. [I] Esquema recomendado: `ide2` = ISO del SO, `ide0` = virtio-win; ambos con `media=cdrom`. [I] Con `q35` el CD en IDE funciona (es lo que hace la propia interfaz de Proxmox y la guía W11); SATA también vale (`sata0…5`), pero no aporta nada y Windows no arranca de discos SCSI VirtIO sin driver, por eso el CD de drivers va en IDE/SATA. [LAB] arranque de ISO en `ide2` con `machine=q35,bios=ovmf`.

## B. Subir ISO y descargar por URL
**`POST /nodes/{n}/storage/{s}/upload`** [H][ST][HS]:
- `multipart/form-data` obligatorio (`Content-Type: multipart/form-data` con `boundary`); campos: `content` (enum `iso|vztmpl|import`), `filename` (**la parte de archivo**; «The name of the file to create. Caution: This will be normalized!», máx. 255; `normalize_content_filename`), opcionales `checksum` + `checksum-algorithm` (`md5|sha1|sha224|sha256|sha384|sha512`, se exigen juntos). `tmpfilename` lo pone el servidor; pasarlo da «'tmpfilename' query parameter is not allowed for file uploads».
- Exige `Content-Length` («upload without content length header not supported»). No hay tamaño máximo explícito: el límite `limit_max_post = 512 KiB` solo aplica a peticiones que no son subidas [HS].
- pveproxy escribe el fichero en `/var/tmp/pveupload-<md5>` (modo 0600) **del nodo que recibe la petición**: hace falta espacio libre en el sistema de ficheros raíz de ese nodo igual al tamaño de la ISO; si falta: «No space left on device» en el log de pveproxy y la conexión se corta (`Broken pipe`/`Empty reply`) [HS][F152453][F113451].
- Permiso: `Datastore.AllocateTemplate` en `/storage/{s}` («allocate/upload templates and ISO images» [DU]). El storage debe tener el content configurado: «storage '$storage' does not support '$content' content».
- Validación: `iso` → extensión `.iso`/`.img`; `import` → `SAFE_CHAR_CLASS_RE+` + `UPLOAD_IMPORT_EXT_RE_1 = qr/\.(ova|qcow2|raw|vmdk)/` («invalid filename or wrong extension»); si es `ova` se comprueba que contenga un `.ovf`; si es imagen se valida con `file_size_info(..., untrusted=1)` (rechaza «backing file not allowed for untrusted image», `data-file`) [ST][SS][SP Plugin.pm].
- Devuelve **UPID** de una tarea `imgcopy` que verifica el checksum, copia (`cp` si el storage es local al nodo; `scp` interno al nodo destino si `{node}` es otro del clúster: eso es SSH **entre nodos**, no del usuario) y borra el temporal. «NOTE: we simply overwrite the destination file if it already exists» → **sobrescribe sin aviso**. La app debe comprobar antes si el `volid` existe.
- **Tokens de API.** [H] En PVE 6.3 el personal de Proxmox dijo «file uploads are not implemented for API tokens (yet)» [F87334]. [H] El código actual extrae el token (`PVEAPIToken`) también en subidas y lo reenvía al hacer proxy a otro nodo [HS]. [H] El bug #4344 (subida fallaba sin `Content-Type` en la parte del fichero, afectaba a `requests`/proxmoxer) se corrigió en `libpve-http-server-perl 4.1-6` (2023, antes de 8.0) [B4344]. [H] En PVE 8 un caso del foro con 403 se resolvió al quitar la «privilege separation» del token (= el token no tenía el privilegio) [F152453]. [I] En 8.0–9.2 la subida con token funciona si el token tiene `Datastore.AllocateTemplate`; la app debe enviar la parte `filename` **con** `Content-Type` (p. ej. `application/octet-stream`) por seguridad. [LAB] obligatorio: subir con token en 9.2 y verificar sha256 del resultado.
- [I] Para ISOs de varios GiB conviene no cargar el fichero en memoria (`requests` con `MultipartEncoder` de `requests-toolbelt` o fichero abierto en modo binario) y mostrar progreso por bytes enviados; el servidor no ofrece progreso de recepción.
- **Borrar un ISO** (`DELETE …/content/{volid}`) exige `Datastore.Allocate` [SC]: la app **no podrá deshacer** una subida con el rol mínimo; hay que advertirlo antes de subir.

**`POST /nodes/{n}/storage/{s}/download-url`** [H][ST]:
- Desde PVE 7.0 [RM]. Parámetros: `url` (patrón `https?://.*`), `content` (`iso|vztmpl|import`), `filename`, `checksum`/`checksum-algorithm`, `verify-certificates` (bool, por defecto 1), `compression` (solo para `iso`; descompresión automática desde 8.1 [RM]). Usa `http_proxy` de `datacenter.cfg`. Mismas reglas de extensión que la subida. El storage debe tener el content: «storage '$storage' is not configured for content-type '$content'». Devuelve UPID de tarea `download`.
- **Permisos por versión:** [H] antes del parche #5254: `Datastore.AllocateTemplate` en `/storage/{s}` **y** `Sys.Audit`+`Sys.Modify` en `/` (ambos; es un `['perm','/',['Sys.Audit','Sys.Modify']]` sin `any`) [P5254]. [H] Desde 8.2 (parche aplicado 2024-02-28, publicado en 8.2 [RM]): `Datastore.AllocateTemplate` **y** (`Sys.Audit`+`Sys.Modify` en `/` **o** `Sys.AccessNetwork` en `/nodes/{n}`) [P5254][ST]. Motivo del cambio: el endpoint «permite escanear la red» desde pveproxy. En **8.0 y 8.1** la única vía es `Sys.Modify` en `/` (casi administrador): la app debe decirlo y no pedirlo.
- [H] `GET /nodes/{n}/query-url-metadata?url=…` («Query metadata of an URL: file size, file name and mime type», HEAD HTTP; devuelve `filename`, `size`, `mimetype`) con los mismos permisos de red (`Sys.Audit`+`Sys.Modify` en `/` o `Sys.AccessNetwork` en el nodo) [MN]: sirve para validar la URL y precalcular espacio antes de lanzar la descarga.

## C. Importar disco qcow2 / vmdk / raw
**`import-from`.** [H] Disponible desde 7.2 vía API [RM]. Sintaxis obligatoria `scsi0=<storage>:0,import-from=<origen>` («'import-from' requires special syntax - use <storage ID>:0,import-from=<source>») [QA]. Descripción del parámetro: «Create a new disk, importing from this source (volume ID or absolute path). When an absolute path is specified, it's up to you to ensure that the source is not actively used by another process during the import!» [QD]. Con `efidisk0` + `import-from` hay que dar `efitype` y `pre-enrolled-keys`; con `tpmstate0`, `version` [QA].
**Quién puede usar cada origen** [H][QA `check_storage_access`][SS `check_volume_access`]:
- **Ruta absoluta** (`/ruta/x.qcow2`): `check_volume_access` muere con «Only root can pass arbitrary filesystem paths.» si el usuario no es `root@pam`. → Fuera de alcance (D-24).
- **Volumen gestionado por PVE** (`storage:…`): su tipo debe ser `images` o `import` (código actual). Si tiene VM propietaria (`images`) se exige `VM.Clone` en `/vms/{vmid-origen}`; si es `import`, `Datastore.AllocateSpace` **o** `Datastore.Audit` en el storage origen. Si requiere extracción (solo OVA) se exige `Datastore.AllocateSpace` en el storage de trabajo (`import-working-storage`, «A file-based storage with 'images' content-type enabled»). El disco destino exige `Datastore.AllocateSpace` en su storage. [H] Si el origen es `import`, el fichero se trata como no confiable (`file_size_info(..., untrusted)`), desde 8.3/8.4 [PIMP].
**Content `import` y storages que lo admiten** [H][SP]: `dir`, `nfs`, `cifs`, `btrfs` (`import => 1` en `plugindata`), `cephfs` (sí `import`, pero **no** `images`) y `esxi` (solo `import`). **No**: `lvm`, `lvmthin`, `zfspool`, `rbd`, `iscsi`, `zfs-over-iscsi`, `pbs`. Los ficheros viven en `<path>/import/`; nombres válidos `IMPORT_EXT_RE_1 = qr/\.(ova|ovf|qcow2|raw|vmdk)/` [SS][SP Plugin.pm]. El content `import` lo activa un administrador (`PUT /storage/{id}` requiere `Datastore.Allocate`): la app no lo hará; lo explica.
**Por versión** (hechos del roadmap [RM] + inferencias):
- **8.0–8.1** [H] no existe el content `import`. [I] Solo valdrían orígenes `images` de otra MV (exige `VM.Clone`, es en la práctica un clon) o rutas absolutas (root). **No hay vía sin root para un qcow2 del usuario.** [I][LAB-no-posible] Truco teórico: subir el disco como ISO con extensión `.img` y usar `import-from=storage:iso/x.img`; el código actual lo rechaza (origen debe ser `images`/`import`) y en 8.x no se pudo leer el código (etiquetas no accesibles). **No recomendado**: depende de autodetección de formato de `qemu-img` sobre fichero no confiable.
- **8.2** [H] `import` solo en el plugin `esxi` (asistente). Sin vía para qcow2 propio sin root.
- **8.3** [H] `import` en storages de fichero, pero la subida/descarga se anuncia solo para **OVA**. [I] Un qcow2 colocado por un administrador (SSH) en `import/` podría importarse por API; la app no puede subirlo. [LAB-no-posible] (no hay 8.3).
- **8.4+** [H] subida y descarga de imágenes de disco (`qcow2|raw|vmdk`) al content `import` (`Datastore.AllocateTemplate`) [RM][ST]; [I] `import-from=storage:import/x.qcow2` por API válido desde 8.4 (la GUI llegó en 9.0). **Este es el camino para ProxLaunch.** [LAB] en 9.2.
- **9.0–9.2** [H] igual que 8.4 con paridad en la GUI; 9.1 añade `qm import … --import-from` (CLI, no afecta a la API).
**`qm importdisk` / `qm disk import`** [H] son CLI (requieren shell/SSH); su equivalente API es `import-from` [DQ]. No usar.
**Comportamiento en lote** [I derivado de [QA]/[SP]]: cada `POST /nodes/{n}/qemu` con `import-from` crea su propio volumen y copia con `qemu-img convert` → N MVs = N copias completas; el formato destino lo fija el storage (`raw` en `lvmthin`/`zfspool`/`rbd`/`lvm`; `qcow2`/`raw` en dir/nfs/cifs); el tamaño lógico del disco es el **virtual** de la imagen (no el del fichero qcow2 comprimido) → el cálculo de espacio debe usar `size` virtual; se puede ampliar después con `resize` (no reducir: «Shrinking disk size is not supported» [QA]). La tarea `qmcreate` dura lo que la conversión. Las importaciones concurrentes compiten por E/S: [I] limitar la concurrencia (p. ej. 2) en lotes grandes. Con `live-restore` no aplica (solo PBS) [QA]. [LAB] medir tiempo y formato resultante en `lab-lvmthin`.

## D. Clonar una plantilla
**`POST /nodes/{n}/qemu/{vmid}/clone`** [H][QA]:
- Parámetros: `newid` («VMID for the clone»), `name`, `description`, `pool`, `snapname`, `storage` («Target storage for full clone»), `format` («Only valid for full clone»), `full` («Create a full copy of all disks»; por defecto `!is_template` → de una plantilla sale **linked** salvo que se pida `full=1`), `target` («Target node. Only allowed if the original VM is on shared storage»), `bwlimit`.
- Permisos: `VM.Clone` en `/vms/{vmid}` **y** (`VM.Allocate` en `/vms/{newid}` **o** en `/pool/{pool}` si se pasa `pool`); además «'Datastore.AllocateSpace' on any used storage and 'SDN.Use' on any used bridge/vnet» (comprobado en `check_storage_access_clone`).
- Errores: «can't clone to non-shared storage» (si `target` ≠ nodo y `storage` no es compartido); «storage … does not support vm images»; «parameter 'storage'/'format' not allowed for linked clones»; «can't clone VM to node '$target' (VM uses local storage)»; «Linked clone feature is not supported for drive …» cuando el storage no admite `clone` sobre base; «cannot clone TPM state while VM is running»; «unable to create VM $newid: config file already exists».
- **Bloqueos y paralelismo:** «exclusive lock if VM is running - else shared lock is enough» → la MV origen (plantilla, nunca encendida) se bloquea en modo **compartido** (`lock_config_shared`) y la nueva en exclusivo → **varios clones simultáneos de la misma plantilla son posibles**. Comentario del código sobre «parallel clones keeping them active» confirma que se contempla. Devuelve UPID de `qmclone`. [LAB] lanzar 3–5 clones a la vez y medir.
- 9.2: el VMID del linked clone aparece en el log de la tarea [RM]. 8.4+: el estado TPM siempre se clona completo [RM].
**Linked clone: qué storages** [H][SP `volume_has_feature` → `clone`]: `dir`/`nfs`/`cifs`: `clone.base = {qcow2, raw, vmdk}` pero «clone_image creates a qcow2 volume» (el storage debe permitir formato qcow2); `btrfs`: base `{qcow2, raw, subvol, vmdk}`; `lvmthin`: `{base, snap}`; `zfspool`: `{base}`; `rbd`: `{base, snap}`; **`lvm` (grueso): sin `clone` («can't clone images in lvm storage») ni `template`** (comentados «fixme: add later»). [H][DQ] «It is not possible to change the Target storage for linked clones» y «This requires that the original volume is read-only». Full clone a otro nodo: «The only restriction is that the VM is on shared storage, and that storage is also available on the target node» [DQ]. [I] Para lotes multinodo con storage local hay que tener una plantilla por nodo (o clonar y migrar, fuera de alcance).
**Convertir en plantilla** `POST …/template` [H][QA]: permiso `VM.Allocate` en `/vms/{vmid}`; parámetro `disk` opcional; errores «you can't convert a VM to template if VM is running», «…because VM contains snapshots», «you can't convert a template to a template»; tarea `qmtemplate`. [H][QS `template_create`] recorre los discos, salta CD-ROM y los volúmenes sin feature `template` (LVM grueso), y convierte el resto en base (`vdisk_create_base`, nombres `base-<vmid>-disk-N`). [I] Una MV en LVM grueso puede marcarse plantilla pero solo admite full clone. [DQ] «Such templates are read-only … It is not possible to start templates».
**Detectar plantillas** [H][MC]: `GET /cluster/resources?type=vm` → campo `template` («Determines if the guest is a template»), junto a `vmid`, `name`, `node`, `status`, `lock`, `tags`, `pool`; se listan solo las MVs con `VM.Audit` en `/vms/{vmid}`. Alternativa por MV: `GET …/qemu/{vmid}/config` (`template: 1`), `VM.Audit`.
**Ajustar tras clonar** [H]: esperar a que termine `qmclone` (la nueva MV tiene `lock: clone`); `PUT /nodes/{n}/qemu/{newid}/config` con `cores`/`sockets` (`VM.Config.CPU`), `memory`/`balloon` (`VM.Config.Memory`), `name` (`VM.Config.Options`), `net0` (`VM.Config.Network`) [F1]; `PUT …/resize` con `disk=scsi0&size=+20G` → `VM.Config.Disk` + `Datastore.AllocateSpace`; solo crecer [QA]. [LAB] si `resize` devuelve UPID o es síncrono en 9.2.

## E. Hardware recomendado
**Windows** [H]: `ostype` ∈ `other wxp w2k w2k3 w2k8 wvista win7 win8 win10 win11 l24 l26 solaris` [QS]; guías oficiales: «Microsoft Windows 11/2022/2025» (→ `win11`) y «Microsoft Windows 10/2016/2019» (→ `win10`) [W11][W25][W10]; controlador «VirtIO SCSI single», bus SCSI, caché «Write back» (o «No cache», más seguro), `discard`, IO Thread, red «VirtIO (paravirtualized)», Qemu Agent activado, segundo CD en IDE 0 [W10][W11][W22][W25]. Drivers a cargar en la instalación: `vioscsi\w10\amd64` («Red Hat VirtIO SCSI pass-through controller»), `NetKVM\…`, `Balloon\…`; agente `guest-agent\qemu-ga-x86_64.msi`; resto con `virtio-win-gt-x64.msi` [W10]. [H][DQ] «Some operating systems (such as Windows 11) may require use of an UEFI compatible implementation» → `bios=ovmf` + `efidisk0=<st>:1,efitype=4m,pre-enrolled-keys=1` (por defecto `efitype=2m`, `pre-enrolled-keys=0` → hay que enviarlos [QD]); «Certain operating systems (such as Windows 11) require such a device» → `tpmstate0=<st>:1,version=v2.0` (**por defecto `v1.2`**, hay que enviar `v2.0` [QD]; formato fijo raw hasta 9.0, qcow2 posible en 9.1+ [RM]). «For Windows guests, the machine version is pinned during creation» [DQ]. q35: la doc solo lo liga a PCIe passthrough [DQ]; [I] la interfaz de Proxmox y D-24 lo fijan para Windows 11/2022/2025; mantener `q35`. [RM 8.4] OVMF desactiva PXE sin `rng0`: si el perfil arranca por red con UEFI, añadir `rng0`.
**Drivers virtio-win** [H]: ISO estable `https://fedorapeople.org/groups/virt/virtio-win/direct-downloads/stable-virtio/virtio-win.iso` (redirige al nombre versionado), «latest» en `…/latest-virtio/virtio-win.iso` («may be pre-release quality») [VW]; «digitally signed by Red Hat» [WV]; recomendaciones (a 2026-09): 0.1.271 sin problemas conocidos, evitar 0.1.285 con Server 2025 y E/S intensa [WV]. **Licencia:** [H] el repositorio de drivers tiene una licencia con texto de 3 cláusulas tipo BSD (copyright Red Hat 2009-2025, Google, Virtuozzo, IBM) [VL]; el README de empaquetado no declara licencia de la ISO [VW]. [I] La app **no debe redistribuir** la ISO: que el **nodo** la descargue con `download-url` (si hay permisos) o que el usuario la descargue y la suba; así ProxLaunch solo maneja una URL. [LAB] tamaño real de la ISO (`query-url-metadata`).
**Red Hat / Linux** [I]: `ostype=l26`, `scsihw=virtio-scsi-single`, disco `scsi0` con `iothread=1,discard=on`, red `virtio`, `bios` seabios u ovmf indistinto (RHEL arranca en ambos), sin TPM. Limpieza: borrar MVs (D-21) y ficheros subidos (requiere `Datastore.Allocate` → hacerlo como root del lab) y desactivar `import` en `local`.

**Recomendación de diseño (accionable):**
1. Detectar versión (`GET /version`) y **capacidades**: `import` disponible si versión ≥ 8.4 **y** existe un storage visible con `import` en `content`; `download-url` ofrecido si versión ≥ 8.2 y `GET /access/permissions` muestra `Sys.AccessNetwork` en `/nodes/{n}` (o `Sys.Modify` en `/`); subida ofrecida si hay `Datastore.AllocateTemplate` en algún storage con `iso` (o `import`).
2. Mensajes: 8.0–8.3 sin importación: «Tu Proxmox X no permite importar discos sin ser administrador del servidor. Opciones: instalar desde ISO o clonar una plantilla. Desde Proxmox 8.4 sí es posible»; sin storage con `import`: «Pide al administrador que active el contenido "Import" en un storage de tipo directorio/NFS/CIFS»; 8.0–8.1 sin `download-url`: «Descargar desde URL exige permisos de administrador en esta versión; descarga la ISO en tu equipo y súbela».
3. Rol: ampliar `ProxLaunchCreador` con `VM.Config.Disk` (orden de arranque, resize), `VM.Clone`, `Datastore.AllocateTemplate`; `Sys.AccessNetwork` en `/nodes` opcional; **no** pedir `Datastore.Allocate` (la app no borra ISOs; avisar «la subida no se puede deshacer desde la app»). Añadir `VM.Config.CDROM` solo si se edita el CD de MVs existentes (no previsto).
4. Flujo ISO: `ide2` SO + `ide0` virtio-win (Windows) con `media=cdrom`; `boot=order=scsi0;ide2;net0`; Windows: `ostype=win11|win10`, `machine=q35`, `bios=ovmf`, `efidisk0=…,efitype=4m,pre-enrolled-keys=1`, `tpmstate0=…,version=v2.0` (Win11/2022/2025), `scsihw=virtio-scsi-single`, `scsi0 … iothread=1,discard=on`, `net0=virtio`, `agent=1`. Subida con `checksum` sha256 calculado localmente; comprobar existencia previa del `volid`; estimar espacio con `query-url-metadata` cuando haya permisos.
5. Flujo importación (≥ 8.4): un solo upload al storage `import` (verificado por checksum) y N creaciones con `import-from`; concurrencia limitada; espacio = tamaño **virtual** × N; `format` solo en dir/nfs/cifs (`qcow2`); ofrecer «ampliar disco» tras importar (`resize`).
6. Flujo clon: listar plantillas con `/cluster/resources?type=vm&template=1`; proponer **linked** cuando el storage de la plantilla tiene feature `clone` (tabla §D) y **full** en LVM grueso o cuando se quiere otro storage/nodo; lanzar en paralelo (lock compartido) con límite; luego `config`+`resize` por MV.
7. Las conversiones a plantilla, la activación de `import` y el borrado de ficheros quedan **fuera** de la app (explicación + enlace a la guía).
